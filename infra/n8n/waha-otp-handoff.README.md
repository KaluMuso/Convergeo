## Contract and replay reservation

The Edge Function sends `{version,requestId,timestamp,deadline,phone,otp}` to a dedicated HTTPS n8n webhook with Header Auth and `X-Convergeo-OTP-Signature`. The signature is lowercase hex HMAC-SHA256 over `v1\n<timestamp>\n<requestId>\n<deadline>\n<phone>\n<otp>` using a **separate** secret. The n8n Crypto node computes the HMAC from a credential. The Code nodes validate shape, time, recipient and digest before the send node. The Edge Function accepts only a 200 response of exactly `{accepted:true,requestId:<same id>}` after WAHA returns a message ID.

The disabled WAHA HTTP Request v4.2 node explicitly refuses redirects and disables credential forwarding across origins. Both settings are required because [n8n 2.30.6 follows redirects by default for v4 nodes and defaults cross-origin credential forwarding on for versions before 4.4](https://github.com/n8n-io/n8n/blob/n8n@2.30.6/packages/nodes-base/nodes/HttpRequest/V3/HttpRequestV3.node.ts). Synthetic 307/308 response fixtures cannot produce an accepted OTP receipt.

The `Reserve Request ID` Postgres node uses an atomic `INSERT ... ON CONFLICT DO NOTHING RETURNING` before WAHA. A duplicate produces no downstream item, so the send does not run. The owner approved a dedicated private schema in the **vergeo-sandbox staging Supabase project** (`iyasmrmbcrvlfxpzescb`, database `postgres`), not the n8n SQLite execution store or Supabase Auth tables. The additive shared migration `supabase/migrations/20261009124801_otp_replay_reservation.sql` creates only the private `otp_replay.otp_delivery_replay` table with RLS and no policies or login. The separate `infra/staging/supabase/otp-replay-login.sql` creates the passwordless `n8n_otp_replay` login, policies, search path, and column-limited grants. It is outside the shared migration chain and must run only through `scripts/ops/apply-otp-replay-login-staging.py`, which pins the approved Supabase project, checks its identity and effective privileges, and verifies the result. Neither step has been applied to staging. The owner must set the login password through a private secure channel after independent review, never in SQL source or chat.

For a later approved application, check out the reviewed commit and confirm the Supabase CLI dry run for **vergeo-sandbox** lists exactly `20261009124801_otp_replay_reservation.sql` as pending. Do not run `db push` if any other migration is pending; it applies the pending chain. Apply that single migration only after the independent ledger and project check, then run the staging bootstrap with the owner's privately supplied `SUPABASE_ACCESS_TOKEN`. The runner defaults to a no-network render check; `--apply` is the explicit staging write. Its read-only preflight requires the table and RLS, no existing login, no PUBLIC schema CREATE, and no PUBLIC-reachable security-definer function. Its postcheck audits effective schema, column, table, role membership, and callable security-definer privileges. A separate owner-side password step is required; this runner leaves the password unset. No step in this document authorizes applying a migration, setting a password, or activating the workflow.

Use a dedicated Postgres credential with TLS required and certificate checks enabled. The role has only schema `USAGE`, table column `INSERT(request_id, expires_at)`, and `SELECT(request_id)` for `RETURNING` and conflict handling ([PostgreSQL privilege rule](https://www.postgresql.org/docs/current/sql-insert.html)); it cannot read expiry, delete rows, or access Auth/business tables. The stored values are random request IDs and expiry times; no phone, OTP, or message body. Retain reservations for at least one day, then purge expired rows through a separately authorized maintenance path with no `DELETE` grant to the n8n login. A database outage must stop delivery. A reservation followed by WAHA failure also blocks retry of the _same_ request ID; requesting a fresh Supabase OTP may create another ID. Concurrent duplicates are serialized by the database primary key. This does not prevent a new signed request ID from producing another message, nor prove handset delivery or exactly-once behavior.
