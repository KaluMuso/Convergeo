## 2. Gaps closed on this branch (priority order)

1. **Ads**
   - Typed ad targets: additive `ad_placements.target_kind/target_id` (`listing | product | service | event | vendor`), validated on create/edit (target must exist and be customer-visible). `cta_href` stays for external/legacy ads.
   - Serve-time guard: a placement whose target is no longer customer-visible (listing not active / product not active / service not active / event not published / owning vendor not active), or whose advertiser vendor is not active, is dropped by `load_live_placements` — so it vanishes from feed slots and the hero carousel even while its status is `active`.
   - Merch resolver: expired / paused / out-of-window non-default slots never render (fallback only to an active `is_default` slot or an active evergreen slot).
   - Admin UX: edit (draft/scheduled/paused), pause/resume, remove (end with a required reason) through `ConfirmModal`; target picker; Africa/Lusaka window display; shared Loading/Empty blocks; tokens only.
2. **Catalog control** (listings, services, events, vendors)
   - `catalog_moderation_holds` + `public.moderate_catalog_entity()` / `public.release_catalog_moderation()` guarded SQL functions (lock row, validate edge, write hold with required reason). Edges: listing active|paused|draft→paused (hide) / →removed (block); service →paused (hide/block); event published→draft (unpublish); vendor active→suspended (block). Restore returns the entity to the status recorded on the hold (vendor restore requires approved KYC).
   - DB trigger: while an active hold exists, nothing (vendor API, service role, PostgREST) can move the entity back to its public status — only `release_catalog_moderation()`.
   - Cart/checkout: lines whose vendor is not active are blocked with the existing non-disclosing `cart.listing_unavailable` conflict (read path, checkout, order create, add).
   - Admin API `/admin/catalog/*` (search, moderate, restore, edit display fields) + audit_log row per mutation; admin UI "Catalog control" page with confirmation + required reason.
3. **Permissions**: every new route registered in `_ADMIN_ROUTE_PERMISSIONS` with the existing permission for its entity (`products.manage` listings, `services.read` → see decisions, `events.manage` events, `vendors.manage` vendors, `ads.manage` ads).

## 3. Decisions needed (founder)

- **Vendor-paid ads**: `paid_amount_ngwee` / `payment_reference` are record-only. Charging vendors (Lenco invoice/escrow, refunds on early end, VAT) needs a product decision — not built.
- **Category/search sponsored slots**: not built; needs a ranking + labelling rule (how many per page, relevance floor).
- **Service moderation permission**: the RBAC set has only `services.read`; mutating services is gated to `products.manage` for restricted roles here. A dedicated `services.manage` would be a new permission — left to the RBAC audit.
- **Event unpublish with sold tickets**: unpublish hides the event page/browse; issued tickets stay valid. Cancel-with-refund remains the organiser/finance flow.
