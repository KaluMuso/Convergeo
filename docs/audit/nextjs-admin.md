# Next.js feature audit: apps/admin (2026-11-27)

Scope: `apps/admin` (Next 15.5.29, App Router, 63 page routes, ~23k lines of route code).
Measured with `next build` (webpack, fonts mocked offline) on master `8e465c22`.
Admin stays a separate hardened origin behind Cloudflare Access plus the role gate; none of
the changes below touch middleware, Access verification, the allowlist or security headers.

## Architecture in one paragraph

Every admin page is a thin **static server shell** (`generateStaticParams`, `AdminPage`
header, translated title) around a **client board** that fetches from the API with the
browser Supabase token. All authorisation that matters happens in the API
(`require_admin_scope` + `_ADMIN_ROUTE_PERMISSIONS`, covered by
`tests/test_admin_role_route_matrix.py`). The Next side adds (a) middleware: Cloudflare
Access JWT check + "admin-like role" gate, and (b) the client shell, which fetches
`/admin/me/permissions` and hides nav items / denies routes. There is no server-side data
fetching, so nothing sensitive is rendered by the server; the cost is that every page pays
JS download, hydrate, permissions round trip, data round trip in sequence.

## Debug walk (routes, i18n, links, contracts)

- **Routes**: all 63 pages walked. Every page maps to a nav item or is an auth/personal
  route (now enforced by `admin-page-contract.test.ts`).
- **Raw i18n keys**: static check of every literal `t("...")` against the `en` bundles for
  each `useTranslations`/`getAdminTranslator` binding: 0 missing keys. (Dynamic template
  keys not checked.) `admin.nav.dispatch` added with #950.
- **Dead links**: every `/${locale}/...` href resolves to an existing page; the dashboard
  deep link `/orders?status=placed` works (and now round-trips, #951).
- **API contracts**: extracted every `/admin/...` string used by admin and matched it to the
  FastAPI OpenAPI paths (209 admin paths): all fixed paths exist; the dynamic ones
  (`/admin/flags/{id}/{action}`, `/admin/intake/{id}/{action}`, `/admin/branches/{id}/{decision}`,
  door-payment actions, catalog `{tab}/{id}/...`) were checked against the action unions in
  code and exist in the API. Method/response-shape checks were left to the existing
  per-board tests.
- **Permission overlap**: for each nav item, the page's GET/POST endpoints were compared with
  `_ADMIN_ROUTE_PERMISSIONS`. Only `orders` -> dispatch endpoints had no overlap
  (`logistics.manage`), fixed in #950. Informational: a `logistics.manage`-only user has no
  permitted home page (`/` needs `analytics.read`), so after login they land on a denial and
  must click Dispatch; a role-aware landing redirect would fix that.
- **Not found**: no runtime errors found by reading; I could not run the app against a live
  API in this environment.
